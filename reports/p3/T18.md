# T18 report — p3: does T15_final blocking lift the matcher? (India group)

Status: partial (updated as the Kaggle runs land). Verdict: pending the T15_final side. The baseline is done (below).

## Setup
- **Tool:** `exploration/p3/dense_cv_group_prune.py` runs p2's `exploration/p2/dense_cv_group.py` **unchanged**
  (its JSON is written as usual; copies are in `exploration/p3/dense_cv/`). p1's `dense_cv.build_pairs` /
  `oof_scores` are wrapped, not modified, so the same run's pairs, out-of-fold final scores and folds stay in memory.
- **Pruning, out of fold, like `Pipeline._prune`:**
  - The configured stage-1 scorer (`prune.scorer`, on `prune.features` only) is fitted on each fold's training
    candidates and scores the held-out fold.
  - Per S1, keep score ≥ `min_score` (0.005), best first, at most `max_per_s1` (10).
  - The same final-model OOF scores are decided on the survivors (p1_assign, threshold 0.7), so pruned true pairs count
    as misses.
- **Memory hygiene:** results are unchanged, but the 3-blocker run was OOM-killed twice at the 30 GiB limit (below). The
  wrapper now clears the blockers' token caches after blocking and calls `malloc_trim` at build_pairs'
  `gc.collect()` before the feature concat.
- **Group:** India. Blocking, IDF and density of the group are exact.
- **Machine:** Kaggle CPU kernels (4 vCPU, 30 GiB cgroup, no swap). F0.5 is deterministic given data, config and seeds.

## Memory (the lead asked to report it rather than shrink the blocker)
- **The E5 stacks do not fit a 30 GiB machine on the India group, even for the baseline.** `T13_sub4` (submission #4,
  29.44M pairs, 1 blocker) was killed twice:
  - Run 1 at the feature concat (peak 27.5 GB after p1_e5).
  - The warm retry got through the concat and finished fold 0 (best_iteration 875, **peak 31.1 GB**), then was killed in
    fold 1.
  - Logs: `exploration/p3/kaggle_t18a/out/`.
- So the as-asked pair (T13_sub4 vs T15_sub5) needs phoenix. The no-E5 pair isolates the same blocking lever:
  identical stacks minus the same feature set.
- **T18_p3_noe5 (3 blockers, 30.89M pairs):** OOM-killed (rc 137) twice on the 30 GiB box.
  - Run 1 was killed after all three feature sets were computed (peak 25.9 GB so far), at the concat of the feature
    caches.
  - The same-session retry with warm caches was killed at the same concat.
  - The baseline (29.44M pairs, 1 blocker) passes that point, then peaks at 28.4 GB in the LightGBM folds.
  - Logs: `exploration/p3/kaggle_t18d/out/`.
- **The +1.45M pairs (+4.9%) and 4 extra blk columns put the 3-blocker run over 30 GiB** with the current dense-CV
  code, which holds the pairs table, all feature columns and LightGBM's fold copy at once.
- **On phoenix (128 GB)** this is not an issue. Full-train dense CV of T15_sub5 is ~77M pairs vs ~73M for T13_sub4.
