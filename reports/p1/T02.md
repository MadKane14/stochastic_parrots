## What I did
- Env/data on phoenix, eval lock, requirements pin (scipy 1.15.2), round-2/3 planning for p2–p4.
- Blocker `p1_compound`: IDF cosine over unigrams + compound keys (name-word pairs, address bigrams, number×word,
  number×name) within equal-country-string groups, forward top-30 + reverse top-3 per S2/S3 record; ~12 min per
  full dataset (4 workers; memory-bound).
- Matcher: `p1_match` (string, IDF, number, group-relative features; chunked, float16), `p1_extra` (romanized
  skeletons via `p1_romanize`, number edit distance, token replacement), `p1_lgbm`, `p1_assign`.
- Dense CV + LOCO harness (`exploration/p1/dense_cv.py`), error analysis, decision-rule and stacking tools.

## What I learned
- val_v1@0.1 is ~10× less dense than test and hid the main error class (sibling / distractor records): I-15..I-18.
- Unseen-country penalty at density is ~0.065 (LOCO); IDF within country groups + script-agnostic features cut it
  by 0.018 (I-19, I-20). France (15% of test) is probably still our weakest country.
- Blocking misses are the largest remaining loss at density (0.0129 of 0.030).
- base.yaml's HGB `max_iter: 300` leaked into LightGBM via config deep-merge and capped boosting (I-21).

## Surprises / bugs / data issues
- Test has ~24% more S2/S3 records per S1 than train (more distractors) → test likely harder than dense CV.
- First test run OOM-killed at the 60 GB cap (3 copies of float32 features) → float16 + preallocated matrices.
- `tmux has-session -t ber` prefix-matches `ber2` (use `-t =ber`); `_component_fp` reads source at call time
  (editing a component during a run invalidates its cache key).
